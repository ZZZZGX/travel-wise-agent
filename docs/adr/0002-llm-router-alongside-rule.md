# ADR 0002 · LLM 路由与规则路由并存，而非替换

**状态**：已采纳　**日期**：2026-08

## 背景

Phase 1 要引入 LLM Function Calling。直觉做法是把 `router.py` 换成 LLM 实现，
"这样才像 Agent"。但这会同时失去三样东西：零成本的回归基线、离线可跑的 CI、
以及判断"LLM 到底带来了什么"的参照系。

## 决策

**新增而不替换。** 引入 `Router` 抽象，`RuleRouter` 包装既有 `router.py`
（该文件一行未改），`LLMRouter` 用 function calling 实现，两者产出结构相同的
`TravelState`，因而能跑**同一套** `evals/cases.json`。

配套决定：

1. `evals/run_evals.py` 只增加一个**注入点**，默认仍是规则路由——
   `python evals/run_evals.py` 的行为与 Phase 0 完全一致；
2. 新增 `evals/compare_routers.py` 做对照实验，同时报告
   **准确率 / 延迟 / Token 成本 / 降级次数**——只比准确率无法回答"值不值这个价"；
3. `LLMRouter` 失败时可降级到规则路由，但**必须标记 `fell_back`**，
   降级取得的成绩不算在 LLM 头上；
4. 不变量由代码保证而非依赖模型自觉：非法日期丢弃、出发地等于目的地视为抽错、
   scope 非法回落 city。无论谁来路由，这些都不该靠对方守规矩。

## 关于离线回放的诚实性

`ScriptedLLMClient` 回放的是**人工录制的合成响应**，且录制基准来自规则路由，
因此两者成绩必然接近。它 `is_synthetic = True`，对照报告会据此打出警示并
**拒绝给出模型优劣结论**。

这一点必须写死在工具里而不是靠人记得说明：一份显示"LLM 100% 准确"的报告
若不标明数据来源，就是在制造假证据。

## 后果

正面：可离线跑通整条 Tool Calling 链路；有了真正的对照实验框架；
LLM 不可用时系统仍可用。

负面 / 待办：维护两条路由路径有成本；当前用例集对规则路由过于友好
（规则已 100%），需要扩充**改写、噪声、多轮、冲突条件**等更难的用例，
在规则真正吃力的地方再比一次——否则对照实验证明不了什么。
