# 原理、稳定性与已知缺陷

这份文档存在的理由：**让人在决定用不用之前，先知道它做不到什么。**

一个工具最危险的状态不是能力弱，而是能力边界没写清楚——
用的人以为它在做 A，它其实在做 B，而 B 在大多数时候看起来也像 A。

---

## 一、核心原理

### 1.1 「什么时候买机票最划算」是怎么算的

**先说结论：这是一次近似替代，不是价格预测。**

理想的做法是拿到「同一班航班、同一出行日，在过去 N 天里的价格序列」，
看它怎么变。但航班接口**只返回当前报价，无法回溯**——
你没法查「8月20号那天，8月29号的票卖多少钱」。

所以本项目做的是：

```
今天这个时点
   ↓ 从明天开始，逐日查未来 N 天的票价
   ↓ 得到一条「价格 ~ 提前天数」的曲线
   ↓ 取曲线最低点对应的提前天数 M
建议购票日 = 出行日 − M
```

**用横截面代替时间序列。** 前提假设是：
「提前 M 天买最便宜」这条规律，在相邻出发日之间大致稳定。

这个假设成立时结论有用，不成立时结论会错得很自信。

### 1.2 三种口径，为什么要分开报

| 口径 | 怎么算 | 什么时候可信 |
|---|---|---|
| **逐航班共识**（主） | 只看全窗口都在飞的航班，统计各自最低点落在哪天 | 有半数以上航班在同一天见底时 |
| 面板中位价 | 每天在同一批可比航班上取中位数 | 作为共识的交叉验证 |
| 全量最低价（仅对照） | 每天在**所有**航班上取 min | **容易被单日特价定住**，只作对照 |

第三种最直观也最容易骗人：某天冒出来一班只飞那天的中转特价，
就能把整条曲线拉平。它不是同一班飞机在不同日期的价格，跨日期比较不成立。
所以它在输出里明确标着「仅对照」。

### 1.3 目的地推荐的双轨

| 轨道 | 数据来源 | 调用成本 |
|---|---|---|
| **名录轨** | 内置 A 级景区 CSV | 0 次 |
| **发现轨（一层）** | 按场景词拼搜索入口 URL | 0 次 |
| **发现轨（二层）** | 搜索接口取回帖子 → 抽地名 → 按提及次数过滤 → 再拼一次 URL | 每个场景词 1 次 |

二层未配置搜索源时会明说「未启用」，**不会用模型编一份地点清单顶上**。

## 二、稳定性分析

### 2.1 稳的部分

**运行时零第三方依赖。** 只用标准库。不会因为某个包升级而挂掉，
也不存在依赖链上的供应链风险。

**失败不会假装成功。** 接口挂了、字段对不上、额度用完，
输出里都会如实说明「未获取到数据」，不会用推测值填补。
这条有专门的测试守着（`tests/test_agent.py::TestToolFailure`）。

**一个技能失败不拖垮另一个。** 机票接口挂了，目的地推荐照常交付。

**双数据源容错链。** 主接口抛错（超时/401/429/格式变更）自动切备用；
主接口返回空列表视为「当天确实没航班」，不会再打备用浪费额度。

**副作用必须经过人。** 创建提醒这类写操作只生成预览，
拿到明确确认才执行，且重复确认不会重复创建。

**README 里的数字由 CI 核对。** 测试数、评测通过数都是实跑一遍再和文档比对，
对不上就构建失败。文档不会悄悄过期。

### 2.2 不稳的部分

**上游接口的字段可能变。** 这是最大的外部风险。
缓解手段是 `TRAVELWISE_STRICT_FIELDS=1`——字段对不上直接报错，
而不是猜一个继续跑。**强烈建议生产环境打开。**

**代码共享航班导致行数虚高。** 同一架飞机会以多个销售航班号重复出现。
项目会做合并，但合并依据是「起降时刻 + 机型」，
遇到接口数据不规范时可能合并不全。

**航班号在不同日期不一致时，横向比价失效。** 输出里有「航班行覆盖率」告警：
覆盖率低说明多数航班号只在少数几天出现，此时「同一行 = 同一航班」的前提不成立。
遇到这个告警要人工抽查两天核对。

**LLM 路由会降级。** 模型报错时自动退回规则路由并明确告知。
好处是不中断，坏处是**你必须去看那行提示**，否则会以为模型在工作而其实没有。

**缓存是按天的。** 同一天重复查同一航线读缓存。
如果票价在一天内剧烈波动，缓存会让你看到旧值。

## 三、已知缺陷

按严重程度排序。**这些都是真实存在的问题，不是"未来规划"。**

### 3.1 方法论层面

| 缺陷 | 影响 |
|---|---|
| 横截面近似不适用于跨节假日 | 出行日在国庆/春运而扫描窗口在平日时，结论基本不可用。**误差随「离出行日还有多远」收敛**——窗口开始覆盖同类需求日期后会回到正常水平 |
| 窗口截断 | 最低点落在窗口最后一天时，真谷底可能更远。输出会告警，但**不会自动放宽窗口**（那会超预算） |
| 发现轨的排序信号是「提及次数」 | 它衡量的是流量热度，不是质量。营销号互相抄稿会被放大——**这个方法擅长找共识，不擅长找小众**，和"小众景点"这个场景词的目标相反 |
| 同星期几对齐需要 ≥2 个样本 | 窗口 7 天时常常不可用，会明确跳过而不是用 1 个样本硬算 |

### 3.2 数据层面

| 缺陷 | 影响 |
|---|---|
| 内置景区名录是抽样，不是全量 | 857 条，全国 A 级景区有上万家。沈阳这类城市只有 1 条记录 |
| 城市三字码表 159 行 | 生僻城市解析不出来。规则是「宁可多问一轮，不要瞎填」 |
| 票价是航司基准最低可售价 | **不含平台优惠券、立减、会员权益**。实际支付可能更低。本项目回答的是"哪天哪班便宜"，不是"最终付多少钱" |

### 3.3 能力层面

| 缺陷 | 影响 |
|---|---|
| 规则路由在难例上 4/19 | 「29号」「8.29号」这类写法认不出；否定（"别给我查机票"）无效；范围外硬凑（把"高铁票"当机票办）。配 LLM 路由可缓解 |
| 无跨会话长期记忆 | 多轮续跑管的是同一段对话内的状态延续；「他一般从上海出发」这类长期偏好没有 |
| 可观测性不是生产级 | 有调用链追踪，但没有采样、没有上报后端、没有跨请求聚合。它解决"这次为什么跑错"，不解决"这周错误率多少" |
| 只做机票和目的地两件事 | 火车票、酒店、签证、打车都不支持，会明确拒绝而不是硬凑 |
