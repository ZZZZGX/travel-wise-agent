# TravelWise 决策规范（Source of Truth）

> **本文件是业务规则的唯一权威来源。**
>
> - `prompts/*.md` 是本规范面向 LLM 的表述，从本文件派生；
> - `src/travelwise/` 是本规范的代码实现；
> - `evals/cases.json` 是本规范的可执行断言。
>
> 三者若出现分歧，**以本文件为准**，并应补一条 Eval 用例把分歧固化成回归保护。
> 修改任何业务规则时，请按 规范 → Eval → 代码 → Prompt 的顺序推进。

---

## R1 · 意图路由

| 情形 | 判定 | 理由 |
|---|---|---|
| 抽到**完整航线**（出发地 + 目的地）且未提玩什么 | flight | 明确的机票请求，不附赠景点清单 |
| 只问玩什么 | destination | — |
| 既问机票又问玩什么 | flight + destination | — |
| 只有**单个目的地** + 出行动词（去/飞/到） | flight + destination | 诉求不明，两件事都办，缺参数再问 |
| 火车票 / 酒店 / 签证 / 打车 / 值机 | 拒绝 | 超出能力，不用相近能力硬凑 |

## R2 · 参数抽取

- 必需参数缺失 → **标记 missing 并追问**，不猜、不填看似合理的值。
- 相对时间先换算成具体日期并向用户复述确认。
- 出发地与目的地抽成同一城市 → 视为抽错，按缺失处理。
- 时间词不得粘入地名（「月底上海」应抽出「上海」）。

## R3 · 范围控制（Scope）

- **落地城市 ≠ 玩乐范围**，两个参数必须分开抽取。
- 用户说城市 → `scope=city`；说省 / 自治区 → `scope=province`。
- **禁止因结果数量少而自动扩大范围。** 数量少是事实，如实说明后**征询**用户是否扩大。

## R4 · 失败处理

- **Unknown / Failure ≠ Guess.** 工具失败必须明确失败，不得用记忆或推测补数据。
- 严格区分：**取不到数据 = 失败**；**取到了但当天无航班 = 空结果**（不是失败）。
- 外部返回结构无法判定成功与否时 → **判为失败**（宁可误报失败让用户核实，不可误报成功）。
- 缓存等可选设施不可用时 → 显式返回不可用，调用方跳过，不假装可用。

## R5 · 模块隔离

一个技能失败不得拖垮另一个。机票查询失败时，目的地清单照常交付，并说明机票为何缺失。
缺参数只挡住对应的那个技能，不连坐。

## R6 · 副作用与人工确认

```
准备 → 预览 → 用户确认 → 执行 → 如实回报
```

- **没有 Approval = 不执行。** 默认不发生任何副作用。
- 即使用户说「直接帮我设」，**仍须先出预览**。
- 覆盖：创建提醒 / 备忘、发送消息、未来的预订与支付。

## R7 · 数据诚实

- 景区「适宜季节」字段为空 → 标注**「季节未知」**，不得当作「全年皆宜」。
- 名录中不存在的景区不得编造。
- 只返回搜索**结果页**链接，不返回具体帖子——不替用户做内容筛选。

## R8 · 术语纪律（对外描述）

不得混淆以下概念，README 与简历表述同样适用：

| 实际是 | 不得称为 |
|---|---|
| Structured Retrieval | RAG |
| 单次任务 State | Memory |
| Skill | Agent |
| MCP Adapter | MCP Server |
| Rule-based Router | LLM Agent |
| 购票时机启发式 | 机票价格预测模型 |
